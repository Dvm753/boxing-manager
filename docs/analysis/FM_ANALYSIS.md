# Boxing Manager: аналіз архітектури Football Manager і перенесення на бокс

Документ-основа для проєктування. Мета — зрозуміти, *чому* FM працює як симулятор, які його принципи переносяться на бокс 1:1, які не переносяться взагалі, і яку архітектуру закладати з першого дня.

---

## 1. Що насправді робить FM грою FM

Помилка більшості клонів: копіюють поверхню (таблиці, атрибути 1–20, зірочки) і не копіюють ядро. Ядро FM тримається на семи принципах:

1. **Світ живе без гравця.** Гравець керує одним клубом із ~2000+. Решта клубів керується тим самим кодом ШІ, який має доступ до тих самих дій, що й гравець (трансфери, тактика, тренування). Гравець — не центр світу, а учасник. Це джерело «непередбачуваності», яку люди звуть «живим світом».
2. **Симуляція детермінована і відокремлена від графіки.** Матчевий рушій — це окрема детермінована система; візуалізація — лише спосіб дивитися на її результат. Той самий матч можна «прогнати миттєво» або «подивитися 90 хвилин» — результат ідентичний. У FM26 SI перенесли гру на Unity, але **ядро симуляції (матчевий рушій, тактика, рішення гравців) лишилося власним кодом SI, а не Unity**. Це найважливіший архітектурний урок усієї серії.
3. **Дані — не в коді.** Гравці, клуби, турніри, правила змагань — усе це дані, які завантажуються, а не хардкод. Саме тому існує редактор і десятки років модінгу.
4. **Прихована інформація як механіка.** Реальні атрибути, CA/PA, особистість — приховані. Гравець бачить *оцінку скаутів* із похибкою. Скаутинг — це купівля точності, а не купівля даних.
5. **Час як атомарний цикл.** Гра — це нескінченний `advanceDay()`. Кожен день світ обробляє події: тренування, травми, трансфери, новини, матчі. Усе інше — UI над цим циклом.
6. **Числа — не показники, а входи в модель.** Атрибут 1–20 не «характеристика персонажа», а параметр імовірнісної моделі. CA (Current Ability) — це зважена сума атрибутів із вагами **залежно від позиції**; PA (Potential Ability) — стеля зростання, фіксована на старті (у редакторі часто задається від'ємним числом = випадковий діапазон у кожній новій грі). Якщо атрибути не відповідають CA, гра їх повертає до балансу.
7. **Наратив породжується системою, а не сценаристом.** Історії («він виріс у мене з юнацької команди і забив у фіналі») — побічний продукт чесної симуляції + пам'яті системи про події.

**Урок з FM25/FM26:** FM25 скасували, бо намагалися переробити все одразу; FM26 при новому рушії отримав найнижчі оцінки серії саме через UI/UX, а не через симуляцію. Висновок для нас: **ядро і UI мають жити окремо настільки, щоб UI можна було викинути й переписати, не торкаючись мозку гри.**

## 2. Шарова структура (як її варто розуміти)

```
┌──────────────────────────────────────────────┐
│  UI / Presentation                            │  ← замінний повністю
│  екрани, візуалізація бою, графіки            │
├──────────────────────────────────────────────┤
│  Application / Session                        │
│  команди гравця, збереження, налаштування     │
├──────────────────────────────────────────────┤
│  World Engine (тік дня)                       │
│  календар, ШІ-агенти, економіка, рейтинги,    │
│  прогресія, травми, медіа                     │
├──────────────────────────────────────────────┤
│  Fight Engine (окремий, чистий, детермін.)    │
│  раунд → обмін → удар → пошкодження → суддя   │
├──────────────────────────────────────────────┤
│  Domain Model + Data                          │
│  сутності, схеми, правила, JSON-довідники     │
└──────────────────────────────────────────────┘
```

Жорсткі правила:
- Нижній шар **нічого не знає** про верхній.
- `Fight Engine` — чиста функція: `simulateFight(fighterA, fighterB, context, seed) → FightResult + EventLog`. Жодного I/O, жодного `Math.random()`, жодного доступу до глобального стану.
- `World Engine` не малює. Він генерує події; UI їх читає.

## 3. Мапінг: футбол → бокс

| FM | Boxing Manager | Коментар |
|---|---|---|
| Клуб | Стайбл / зал / промоушен | Гравець може бути менеджером, тренером або промоутером — це різні ролі |
| Ліга, таблиця | Рейтинги санкційних органів | Немає таблиці — є ієрархія і пояси |
| Календар сезону | Немає фіксованого календаря | **Ключова відмінність.** Бої створюються переговорами |
| Трансфери | Контракти, промоутерські угоди, purse bid | Торг — центральна механіка, а не побічна |
| Тактика (формація, ролі) | Стиль + гейм-план по раундах + вказівки в кутку | |
| Матч 90 хв, 38 за сезон | Бій 4–12 раундів, **2–4 на рік** | Радикально інший темп гри |
| Травми | Травми + **накопичена шкода за кар'єру** | Бокс має незворотний знос: підборіддя, ресурс, CTE |
| Форма | Форма + вагозгонка + табірна підготовка | Вага — окрема підсистема, аналога у футболі немає |
| Скаутинг | Скаутинг + розвідка суперника (tape study) | |
| Фінанси клубу | Gate, PPV, спонсори, ТВ, розподіл гаманця | Гроші напряму керують матчмейкінгом |

**Три речі, яких у футболі немає і які мають стати обличчям гри:**

1. **Політика боксу.** Чотири санкційні органи, обов'язкові претенденти, тимчасові пояси, позбавлення поясів, purse bid, «step-aside money», відмови від небезпечних суперників заради збереження «0» у графі поразок. Жоден існуючий боксерський менеджер не змоделював це глибоко — тут ваша ніша.
2. **Матчмейкінг як гра.** У FM ви не обираєте суперника. У боксі вибір суперника — **головне рішення гравця**. Кожен бій — торг між ризиком, грошима, рейтингом і популярністю.
3. **Ціна перемоги.** Війна на 12 раундів приносить пояс і забирає два роки кар'єри. Це має бути в моделі явно.

## 4. Чому існуючі боксерські менеджери не тягнуть

- **Boxing Club Manager (2022)** — легка аркадна менеджерка залу, мілка модель бою, немає світу навколо.
- **World Championship Boxing Manager 2 (2023)** — критики зійшлися на тому, що попри гарний темп гра швидко стає повторюваною через брак глибини.
- **Boxing Manager (iOS)** — найближчий за духом: шоу, промоушени, титульна логіка, ШІ-промоутери. Але це мобільний застосунок із мілкою моделлю бійця і без справжнього симулятора бою.
- **MMA Manager** — цікавий технічно: симуляція бою через ланцюг Маркова зі станами (стійка, клінч, партер). Для боксу такий підхід теж правильний, але простір станів інший.

Спільна вада всіх: **бій — це чорна скринька з кількох кидків кубика**. У FM матч — повноцінна симуляція з поведінкою 22 агентів. Ваша перевага буде саме тут: справжній симулятор бою на рівні обміну ударами.

## 5. Модель бійця

Не копіюйте «один CA». Для боксу краще розділити на три незалежні виміри:

- **Skill Vector** — атрибути (те, що вміє).
- **Condition** — форма, тренованість, вага, свіжість (тимчасове).
- **Wear** — накопичена шкода за кар'єру (незворотне).

Скалярна «сила бійця» (для рейтингів, ШІ і зірочок в UI) — *похідна* від цих трьох, обчислюється з вагами **залежно від стилю**, а не єдиною формулою. Кешується, не зберігається як джерело правди.

### Атрибути (1–20, як у FM — шкала звична і зручна для балансу)

**Технічні:** джеб, прямий, хук, аперкот, робота по корпусу, комбінаційність, контратака, точність, фінти, робота на ближній, клінч, блок/парирування, рухи головою (defence), робота ніг, контроль дистанції, дисципліна захисту.

**Фізичні:** швидкість рук, швидкість ніг, сила удару (KO power), витривалість, відновлення між раундами, фізична сила, баланс, координація.

**Ментальні:** ринговий IQ, холоднокровність, агресія, сміливість, адаптивність по ходу бою, концентрація, інстинкт добивання, працьовитість у тренуваннях, дисципліна (фоли).

**Приховані (гравець їх ніколи не бачить прямо):** підборіддя/durability, серце (здатність терпіти), стійкість до розсічень, схильність до травм, стабільність, професіоналізм, амбіційність, характер у великих боях, дисципліна ваги, брудність.

**Константи:** зріст, розмах рук (reach), стійка (ортодокс / лівша / switch), природна вага, тип статури.

### Стилі (архетипи, що задають *політику поведінки* в рушії)
out-boxer, boxer-puncher, pressure fighter/swarmer, slugger, counter-puncher, switch-hitter, spoiler.

Стиль — не мітка. Це набір ваг у виборі дій та переваг по дистанціях. Саме стилі створюють «камінь-ножиці-папір»: тиск ламає технаря з поганою витривалістю, контратакувальник карає слаггера, довгорукий аутбоксер мучить коротуна.

### Прогресія
- Пік 26–31, спад після, темп спаду прискорюється `Wear`.
- PA-еквівалент: стеля, задана на старті діапазоном (як від'ємні PA у FM) + модифікатор від якості табору.
- Зростання відбувається переважно **в таборі та після боїв**, не щодня.
- Рішення про завершення кар'єри / камбек — ШІ-логіка на основі шкоди, грошей, амбіцій і віку.

## 6. Fight Engine — конструкція

Ієрархія: **Бій → Раунд → Обмін (exchange, ~5–10 с) → Дія → Удар.**
12 раундів × ~20–30 обмінів = 250–350 тіків на бій. Це дешево навіть на телефоні.

### Стани позиції (ланцюг Маркова)
`out of range → long (jab range) → mid (power range) → inside → clinch → ropes/corner → down`

Перехід між станами визначається намірами обох бійців (хто хоче зближення), роботою ніг, силою, витривалістю і стилем.

### Цикл одного обміну
1. **Ініціатива** — хто диктує: f(робота ніг, швидкість рук, ринговий IQ, агресія, втома, стан).
2. **Вибір дії** — з політики стилю + гейм-плану + вказівок кутка + усвідомлення рахунку (з 10-го раунду бієць, який програє, ризикує більше).
   Дії: джеб, подвійний джеб, комбінація, силовий одиночний, по корпусу, фінт, розрив дистанції, вхід у ближній, клінч, глухий захист, чекати контратаку.
3. **Влучання** — `p_land = base(тип удару) × f(точність, швидкість) / f(захист, рухи головою, контроль дистанції) × втома × шкода × модифікатор стану`.
4. **Шкода** — три незалежні накопичувачі: **голова**, **корпус**, **витривалість**. Корпусні удари жеруть витривалість і накопичуються повільно, але зловісно. Удари в голову формують ризик нокдауну.
5. **Травми в бою** — розсічення (з локацією: над оком, бров, ніс), набряк (звужує огляд → мінус до захисту й точності), зламана рука (мінус до сили тієї руки), ребра.
6. **Нокдаун** — поріг за накопиченою шкодою + окремий шанс «флеш-нокдауну» від чистого влучання, модифікований підборіддям, втомою і балансом. Далі рахунок до 10, здатність продовжити, стан «хитається» (hurt state) на N обмінів.
7. **Зупинка** — рефері (стоп при беззахисності), лікар (розсічення), кут (викидання рушника — залежить від тренера і його ставлення до бійця), три нокдауни за раунд (опційне правило комісії).
8. **Суддівство** — три судді, кожен зі своїм **вектором упереджень**: вага чистих влучань / агресії / контролю рингу / захисту, домашня перевага, вага імені, схильність до «стандартних 10-9». Система 10-очок. Звідси — спірні рішення, split decision, скандали, реванші. Це джерело наративу.

### Статистика бою
Лічильники по раундах: кинуто/влучено, джеб/силові, голова/корпус — це готовий CompuBox-екран і основа для аналітики гравця.

### Детермінізм і відтворення
- `seed = hash(saveSeed, fightId)`; PRNG передається явно (mulberry32 / xoshiro), `Math.random()` заборонений у ядрі лінтером.
- Рушій повертає **EventLog** — список подій із таймкодами. Візуалізація бою = програвання логу. Миттєва симуляція = той самий лог без програвання.
- Наслідок: перегляд бою, повтор, «відео» суперника для скаутингу, шеринг боїв — усе безкоштовно з коробки.

### Калібрування (обов'язково, інакше гра буде несмачною)
Golden-master тести: 10 000+ прогонів із перевіркою, що розподіли збігаються з реальним боксом — частка достроково завершених боїв, розподіл раундів зупинки, частка нічиїх і роздільних рішень, кількість нокдаунів на бій, різниця для важких і легких ваг. Ці тести стають гейтом: будь-яка зміна коефіцієнтів, що ламає розподіли, не проходить.

## 7. World Engine

### Цикл дня
`advanceDay()` → обробити: табори і тренування, вагу й відновлення, лікування травм, переговори ШІ, підписання боїв, проведення запланованих карт, оновлення рейтингів, дедлайни обов'язкових захистів, медіа, фінанси, старіння/прогресія (щотижня), генерація молоді (щороку).

### Санкційні органи
4 організації (вигадані аналоги), у кожної власний алгоритм рейтингу, ставка санкційного збору (% від гаманця), правила обов'язкових претендентів із дедлайнами, тимчасові пояси, позбавлення поясів, об'єднавчі бої. Різні органи = різні характери: одна «продажніша», інша жорсткіша.

### ШІ-агенти
Кожен менеджер/промоутер — агент із цілями: берегти рекорд перспективного, довести до титульного шансу, максимізувати дохід, уникати незручних стилів, наповнити власне шоу. Агенти **надсилають і приймають пропозиції через той самий API, що й гравець**. Це принцип симетрії з FM — без нього світ мертвий.

### Економіка
Дохід: квитки (gate), PPV/стрімінг, site fee, спонсори, ТВ-контракти.
Витрати й розподіл: гаманець і його поділ, санкційний збір, % тренера, % менеджера, частка промоутера, табір, спаринг-партнери, медогляди, ліцензії, переїзди.
Популярність бійця (регіональна і глобальна) — основний множник доходу і головна довгострокова валюта гри.

### Вагова система
Природна вага дрейфує з віком і простоєм; згонка має вартість (мінус до витривалості й підборіддя на вечір бою); зважування за добу до бою → часткове відновлення (rehydration); незгін ваги → штраф, втрата права на пояс, скандал. Перехід між ваговими категоріями — стратегічне рішення на кар'єру.

## 8. Дані і генерація світу

- **Все в JSON зі схемами:** вагові категорії, органи, правила, стилі, архетипи, регіони, іменники для генерації, коефіцієнти рушія.
- **Стартовий світ — вигаданий.** Реальні імена бійців = юридичний ризик. Правильний шлях FM: ядро + редактор, а реальні бази робить спільнота.
- Обсяг: активних професіоналів у світі — десятки тисяч, але для гри вистачить **3–5 тис. у MVP** і 15–20 тис. у повній версії. Це на два порядки менше за базу FM (~450 тис. осіб) — отже, продуктивність не буде вашою проблемою, на відміну від SI.
- Генератор світу має відтворювати правдоподібну піраміду: багато середняків, мало топів, регіональні школи боксу (різні розподіли стилів і атрибутів за регіонами), вікова структура, реалістичні рекорди (вигаданий 20-річний не може мати 40 боїв).

## 9. Технічний стек (рекомендація під ваш метод роботи)

- **TypeScript, монорепо.** Пакети: `core-model`, `data`, `engine-fight`, `engine-world`, `sim-cli`, `app-web`.
- `engine-fight` і `engine-world` — **чистий TS без залежностей**, без DOM, без файлів. Запускаються в Node (тести, масові прогони) і в браузері однаково.
- **Web-first**, мобілки через Capacitor (узгоджується з вашим підходом в артилерійському проєкті). Бекенд на Node — лише для онлайн-фази, не в MVP.
- **Збереження:** JSON-снапшот + версія схеми + міграції. Якщо світ виросте — SQLite (op-sqlite на мобілці, sql.js у вебі). Не тягніть Postgres в офлайн-гру.
- **UI:** React. Дизайн-система з першого дня, бо екранів буде 40+.
- **Візуалізація бою:** починайте з текстового play-by-play з таймкодами (це вже 80% емоції), далі — 2D-схема рингу поверх того самого EventLog. 3D не потрібне ніколи.

## 10. Модулі і межі (контракти)

| Модуль | Відповідальність | Заборонено |
|---|---|---|
| `core-model` | сутності, типи, схеми, валідація | логіка симуляції |

Кожна межа — явний TS-інтерфейс. Зміна інтерфейсу = ADR.

## 11. Дорожня карта

**Фаза 0 — ядро без гри (найважливіша).**
Модель бійця + генератор 500 бійців + `engine-fight` + CLI, що прганяє 10 000 боїв і друкує розподіли. Мета фази: **бій відчувається правильно на статистиці**. Жодного UI.

Календар, один стайбл гравця, табір і тренування, рейтинги одного органу, примітивний матчмейкінг ШІ, текстовий перегляд бою, збереження.

4 органи, обов'язкові захисти, промоутери і переговори, економіка, вага і згонка, травми й знос, медіа й популярність, молодь і скаутинг.

**Фаза 3 — обличчя.**
Повний UI, 2D-перегляд бою, статистика, історія кар'єр, рекорди, зал слави.

**Фаза 4 — довге життя.**
Редактор даних, модінг, мобільні збірки, онлайн-ліги.

## 12. Ризики

| Ризик | Пом'якшення |
|---|---|
| Рушій бою «не відчувається» | Фаза 0 закінчується тільки після проходження статистичних тестів |
| Розповзання обсягу | Заморожені межі фаз, ADR на кожну зміну |
| Мало рішень між боями (2–4 бої на рік) | Щільність рішень у таборі + матчмейкінг + політика поясів |
| Дрейф ШІ-агента при вайб-кодінгу | Модулі з жорсткими контрактами, golden-тести як гейт, журнал дій |
| Юридичні ризики з реальними іменами | Вигаданий світ + редактор для спільноти |
| Міграції збережень зламають старі сейви | Версія схеми з першого коміту, тести міграцій |

## 13. Як це лягає на ваш паттерн вайб-кодінгу

- `engine-fight` — ідеальний кандидат на роботу з агентом: чиста функція, повністю покривається тестами, немає UI-контексту.
- **Золоті тести — головний запобіжник від дрейфу.** Агент не може «покращити» рушій непомітно: розподіли впадуть.
- ADR обов'язкові для: формули влучання, моделі шкоди, алгоритму суддівства, схеми збереження, меж модулів.
- Порядок роботи: один модуль → контракт → тести → реалізація → «Погоджено» → наступний.
- У репозиторії тримати `STATE.md` із фактичним станом фаз — це прямо лікує вашу проблему з втратою агентом синхронізації.
