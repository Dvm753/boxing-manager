# Політика контролю змін

## Класи змін

| Клас | Приклад | Що потрібно |
|---|---|---|
| A — Архітектурна | межі модулів, формат сейву, мова/стек, формула влучання, модель суддівства | ADR + «Погоджено» |
| B — Функціональна | новий екран, нове правило органу, новий атрибут | Запис у `ACTION_JOURNAL.md` + тести |
| C — Технічна | рефакторинг всередині модуля, типізація, лінт | Достатньо зеленої збірки |
| D — Текстова | документація, коментарі, переклади | Без гейту |

**Будь-яка зміна коефіцієнтів рушія бою — клас A.** Це не «тюнінг», це зміна правил гри.

## Процедура для класу A

1. Агент формулює **одну** пропозицію: проблема → варіанти → рекомендація → наслідки.
2. Власник відповідає «Погоджено» або ставить питання.
3. Створюється ADR зі статусом `Accepted` і датою.
4. Тільки після цього — реалізація.
5. `STATE.md` оновлюється в тому ж коміті.

## Заборонено
- Об'єднувати кілька рішень класу A в одну пропозицію.
- Реалізовувати ADR зі статусом `Proposed`.
- Змінювати ADR заднім числом. Помилкове рішення скасовується новим ADR зі статусом `Superseded by ADR-XXXX`.
